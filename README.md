# Online Store — Product Catalogue REST API

CIT4242 Advanced Programming · Assignment 1 · KIMEP University
Author: **Laura Kalzhan** (laura.kalzhan@kimep.kz)

A Spring Boot 3 REST service that manages the product catalogue of an online store, persisted in PostgreSQL.

## Tech stack

| | |
|---|---|
| Language | Java 17 (runs on 17 or newer) |
| Framework | Spring Boot 3.5 (Web, Data JPA, Validation) |
| Build | Maven (wrapper included: `./mvnw`) |
| Database | PostgreSQL |
| Tests | JUnit 5 + MockMvc, run on an in-memory H2 database in PostgreSQL mode |

## How to run

### 1. Requirements

- JDK 17 or newer (`java -version`)
- PostgreSQL 13 or newer, running on `localhost:5432`
- Maven is **not** required — use the included wrapper (`./mvnw`, or `mvnw.cmd` on Windows)

### 2. Database settings

The application expects:

| Setting | Default value | Environment variable to override |
|---|---|---|
| JDBC URL | `jdbc:postgresql://localhost:5432/onlinestore` | `DB_URL` |
| Username | `postgres` | `DB_USERNAME` |
| Password | `postgres` | `DB_PASSWORD` |
| HTTP port | `8080` | `PORT` |

Create the database once:

```bash
psql -U postgres -c "CREATE DATABASE onlinestore;"
```

Or, if you have Docker, start a ready-made PostgreSQL with the same settings:

```bash
docker compose up -d
```

The `products` table is created automatically on first start (`spring.jpa.hibernate.ddl-auto=update`).

If your PostgreSQL uses a different password, either edit `src/main/resources/application.properties` or pass it as an environment variable:

```bash
DB_PASSWORD=mysecret ./mvnw spring-boot:run
```

On Windows PowerShell:

```powershell
$env:DB_PASSWORD="mysecret"; .\mvnw.cmd spring-boot:run
```

### 3. Build and start

```bash
./mvnw clean package
java -jar target/onlinestore-1.0.0.jar
```

or simply

```bash
./mvnw spring-boot:run
```

The log ends with `Started OnlineStoreApplication in ... seconds`. The API is at `http://localhost:8080/api/products`.

`./mvnw clean package` also runs the automated tests. They use an in-memory H2 database, so the build succeeds even when PostgreSQL is not running.

## The Product resource

| Field | Type | Rules |
|---|---|---|
| `id` | Long | generated by the database, never accepted from the client |
| `name` | String | required, 2–100 characters |
| `description` | String | optional, at most 1000 characters |
| `price` | BigDecimal | required, positive, at most 2 decimal places |
| `category` | String | required |
| `inStock` | Boolean | optional, defaults to `true` |
| `createdAt` | LocalDateTime | set once, when the row is created |
| `updatedAt` | LocalDateTime | set on creation and again on every update |

## Endpoints

| Method | Endpoint | What it does | Status |
|---|---|---|---|
| GET | `/api/products` | All products | 200 |
| GET | `/api/products/{id}` | One product by id | 200 / 404 |
| POST | `/api/products` | Create a product | 201 / 400 |
| PUT | `/api/products/{id}` | Replace a product | 200 / 400 / 404 |
| DELETE | `/api/products/{id}` | Delete a product | 204 / 404 |
| GET | `/api/products/category/{category}` | Filter by category | 200 |
| GET | `/api/products/search?name=...` | Search by name | 200 / 400 |

## Error handling

Every error, from any endpoint, has the same four fields. `errors` is an empty object when no particular field is to blame. No stack trace, SQL or table name is ever included.

```json
{
  "status": 400,
  "message": "Validation failed",
  "timestamp": "2026-10-27T10:30:00",
  "errors": {
    "name": "Name is required"
  }
}
```

| Situation | Status | `message` |
|---|---|---|
| Body fails validation | 400 | `Validation failed` (each failing field named in `errors`) |
| `name` missing or blank on `/search` | 400 | `Validation failed` |
| Non-numeric id, e.g. `/api/products/abc` | 400 | `Validation failed` (`errors.id`) |
| Body is missing or not valid JSON | 400 | `Request body is missing or malformed` |
| Product does not exist | 404 | `Product with id {id} not found` |
| Unknown URL | 404 | `Resource not found` |
| Wrong HTTP method | 405 | `Method X is not supported` |
| No `Content-Type: application/json` | 415 | `Content-Type must be application/json` |
| Anything unexpected | 500 | `An unexpected error occurred` (details go to the server log only) |

All of these are produced by a single `@RestControllerAdvice` (`GlobalExceptionHandler`). The service throws `ProductNotFoundException`; the controller has no try-catch.

## Assumptions

Where the brief did not say, I decided the following:

1. **Package name.** `com.yourname.onlinestore` became `com.laurakalzhan.onlinestore`.
2. **`inStock` in requests.** It is optional in both POST and PUT. If omitted it is `true`. Because PUT *replaces* the product, omitting it on PUT also sets it back to `true`.
3. **PUT is a full replace.** All required fields must be sent; an omitted `description` becomes `null`.
4. **Client-sent `id`, `createdAt`, `updatedAt` are ignored.** The request records do not have these fields, so they are silently dropped rather than rejected.
5. **Price precision.** Price is stored as `NUMERIC(12,2)` and must have at most 10 digits before and 2 after the decimal point (`@Digits`); otherwise the request is rejected with 400 instead of failing in the database. Prices are always returned with two decimals in stored data (e.g. `7500.00`).
6. **Category filter is case-insensitive and exact.** `/category/electronics` matches `Electronics`, but not `Consumer Electronics`.
7. **Search is case-insensitive and partial.** `?name=lap` matches `Gaming Laptop`.
8. **Search needs a non-blank `name`.** A missing or blank `name` returns 400 rather than every product.
9. **Leading and trailing spaces** are trimmed from `name` and `category` before saving.
10. **Ordering.** Lists are returned in ascending `id` order.
11. **Timestamps** use the server's local time and are shown to the second, as `yyyy-MM-ddTHH:mm:ss`. `updatedAt` changes when a PUT actually changes a value; a PUT that sends exactly the same data leaves it as it was.
12. **Schema management.** Hibernate creates and updates the table (`ddl-auto=update`); no migration tool is used for this assignment.
13. **One error shape for every error**, including 405, 415 and 500, not only for 400 and 404.
